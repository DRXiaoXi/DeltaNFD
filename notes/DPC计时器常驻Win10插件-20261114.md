# DPC 计时器常驻（Win10 研究）插件

日期：2026-11-14（北京时间）。分支 `_br222/s`，HEAD `dd807c595126978c3f3bace937b6ab234abe9cde`，版本仍 Alpha0.935 / 0.9350。

## 用户请求与结论

用户问：能否针对当前测试版「三角帧不掉洲」做一个**使用 DPC 的驱动实现**的 Windows 10 兼容插件。

结论：**可以，已交付本地研究插件** `io.github.drxiaoxi.dpc-timer-hold` 1.0.0（`.dnfdplugin`）。它复现外部视频「4.1 方法」的核心——**保持原版 DPC Latency Checker 1.4.0 运行**：由玩家自备的原版 DPC 自行加载其签名驱动并持有 1.0000ms 系统计时器精度请求，插件只负责启动、核验与释放。插件**不包含、不提取、不复制、不直接加载任何驱动**，也不下载原版 DPC；玩家必须自己提供原版文件，插件按固定字节数与 SHA256 核对身份。

这不是把 DPC 装进插件，也不产生原厂再分发授权；它不消除 CVE-2025-51619，也不代表反作弊兼容。

## 为什么这样实现（关键事实）

1. **原版 DPC 在对话框初始化时就自动请求内核精度。** 对原版 1.4.0 的静态反汇编显示：对话框过程 `0x40F810` 在 `WM_INITDIALOG（0x110）` 分支调用 `0x40F930`；该函数在 `0x40FC0B` 以输入 `0x3E8`（1000 微秒）和 `0x81772008` 控制码提交开始请求。因此「只要 DPC 正常运行」就会持有请求，不需要插件去点按钮或直接驱动设备。
2. **插件只做进程生命周期。** 驱动由原版 DPC 自己 `CreateService`/`StartService`（服务名 `dpclat_driver`，驱动文件 `dpclat.sys`，位于 `%SystemRoot%\System32\drivers\`）；原版退出时通过 `UninstallDrv` 路径 `ControlService`+`DeleteService` 清理。插件只按名称只读查询服务、只正常关闭自己启动的进程；只有遗留服务的类型/启动类型/映像路径都与记录完全一致时才停止并删除它。
3. **不直接驱动 `\\.\dpclat_static_device`。** 直接向设备发 500µs 请求需要让句柄一直存活；一旦关闭句柄，驱动的 `IRP_MJ_CLEANUP` 会释放请求。宿主插件无法在按需后端退出后继续持有句柄（见下），所以本轮选择「运行原版 DPC」这条能自持的路径，持有值是 DPC 固定的 **1.0000ms**，不是 0.5000ms。
4. **宿主合同决定释放方式。** 宿主的修改型操作必须先写「执行意图」，结果必须返回 `backupIds` 才会落账；而任一带待恢复记录会阻止新的 invoke。因此本插件声明 `mutating: true` 的 `start`，释放通过宿主插件管理页的「恢复备份…」执行 `restore`（幂等）。本插件不使用 `continuous`：宿主当前对持续后端不开放 invoke（`InvokeOnceAsync` 在插件运行中返回 BUSY），无法用持续运行承载「开始/停止」两个操作。
5. **不随产品分发。** 规范第 1 节写明插件协议禁止安装内核驱动。本插件自身不安装/加载驱动、不含驱动文件，但会启动一个会安装驱动的第三方程序。这个边界属于项目方判断，因此包与 README 都标注为**本地研究插件，不随产品分发**，不改变产品驱动路径、安装包或线上通道。

## 风险与边界

- DPC 1.4.0 存在 CVE-2025-51619（本地低权限可触发蓝屏）；加载其驱动会扩大攻击面。有效签名不修复漏洞，也不等于反作弊允许。
- 旧式签名驱动在开启 Secure Boot 的部分 Win10 上可能无法加载；插件报告 Secure Boot 状态但不尝试绕过。
- 插件后端是管理员进程，能力声明/协议/独立进程都不是权限沙箱。
- 宿主退出不会自动关闭 DPC：`stop` 只停止后端，不隐式释放外部进程；请用「恢复备份…」或直接关闭 DPC 窗口。若后端被强杀或机器异常重启，`hold-state.json` 记录保留，下次可恢复清理。
- 只正常关闭本次记录且 PID/启动时间/映像路径复核通过的 DPC，不按名称强杀；归属不明的服务不删除。
